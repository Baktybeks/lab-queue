# Текущий способ входа

Студентам выдаются логины вида `asanov_b_r` и пароли преподавателем. Самостоятельная регистрация в интерфейсе убрана. В Supabase Authentication → Sign In / Providers отключите **Allow new users to sign up**, но оставьте Email/password включённым. Анонимный вход выключен. Существующий преподаватель входит по своему email и паролю.

## Создание 30 аккаунтов

Локальный список: `private/students.json`, таблица для преподавателя: `private/student-logins.md`. Папка private исключена из Git и не входит в сборку сайта. Начальный пароль для новых аккаунтов — `12345678`, имя берётся из списка.

Проверка списка без сетевых запросов: `npm run students:plan`.

Из PowerShell в папке проекта выполните:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\create-students.ps1
```

Скрипт запросит Secret key (или legacy service_role) из настроек API Keys Supabase скрытым вводом. Ключ не записывается в проект и не передаётся фронтенду. Он нужен только для локального вызова Admin API. Не присылайте этот ключ в чат. Аккаунты создаются через createUser с email_confirm=true, письма не отправляются. Логин преобразуется во внутренний адрес на зарезервированном домене students.lab-queue.invalid; вводить этот адрес студенту не нужно. Восстановление по почте для таких адресов не работает: пароль меняется преподавателем в Supabase.

Повторный запуск пропускает существующие внутренние адреса и не меняет их пароли. Старые аккаунты на настоящие email сохраняются, автоматически со списком не объединяются.

# Лаба — очередь на сдачу

React + TypeScript + Vite. Статический сайт для GitHub Pages, общая очередь в Supabase.

## Локальный запуск

Node.js 22.18+ или 24+.

```sh
npm install
npm run dev
```

Без `.env` работает явно обозначенный локальный демонстрационный режим. Данные демо хранятся только в этом браузере; управление преподавателя в демо заблокировано. Для админки необходим вход по email и паролю через Supabase. На телефонах общие данные появляются только после подключения Supabase.

## Подключение Supabase

1. Создайте бесплатный проект на https://supabase.com.
2. Для новой базы в SQL Editor выполните актуальный `supabase/schema.sql` один раз. Если предыдущая схема уже установлена, выполните только `supabase/migrations/002_sessions.sql` один раз — основной файл повторно запускать не нужно.
3. В Authentication включите провайдер Email и регистрацию пользователей. Anonymous Sign-Ins не нужен: анонимные пользователи теперь отклоняются сервером. Для новой базы schema.sql включает все изменения. Для уже установленной схемы с сессиями выполните только supabase/migrations/003_student_auth.sql один раз.
4. В Authentication → Users создайте преподавателя с email и паролем. Скопируйте его UUID и выполните в SQL Editor:

```sql
insert into queue_private.admins(user_id) values ('UUID-ПРЕПОДАВАТЕЛЯ');
```

5. Скопируйте `.env.example` в `.env`, укажите URL проекта и публичный publishable/anon ключ из настроек Supabase. **Никогда не используйте secret/service_role ключ во фронтенде.** Перезапустите Vite.
6. Откройте «Преподавателю», войдите с созданным email и паролем. Создайте сессию: выберите дату и укажите группу. До открытия сессии студенты не могут записываться. Обычный аккаунт без записи в admins прав управления не имеет.

Студент регистрируется с именем, email и паролем или входит в существующий аккаунт. На другом телефоне тот же аккаунт остаётся той же личностью. Одновременная повторная запись запрещена. При повторной записи на ту же лабораторную в той же сессии счётчик восстанавливается и приоритет не возвращается. Поле имени заполняется из профиля. При записи отредактированное имя сохраняется в профиле и новой записи атомарно; аккаунт и счётчик не меняются. Самостоятельная регистрация не запрещает одному человеку создать несколько аккаунтов на разные email; для строгого контроля создавайте аккаунты по списку группы и отключите самостоятельную регистрацию. Имена очереди видны всем вошедшим участникам. Не используйте чувствительные данные.

## Правила

- Первый записавшийся становится текущим и не вытесняется новыми записями.
- Актуальная лабораторная даёт приоритет при регистрации. Изменение актуальной лабы влияет на новые записи, сохраняя существующий порядок.
- «Следующий» переносит текущего в конец, снимает приоритет и увеличивает его счётчик «Не ответил» на 1. «Сдал» убирает запись из очереди, сохраняя результат и счётчик в истории. Допзадание не увеличивает счётчик.
- «Доп. задание» выводит текущего из очереди. «Готово» на телефоне возвращает перед обычными и приоритетными записями, после текущего и ранее вернувшихся с допзадания.
- Изменения выполняются транзакционно под общей блокировкой. Устаревшая админская вкладка не сможет случайно переключить другого студента.
- Обновление состояния каждые 5 секунд. При ошибке сайт показывает проблему и предлагает повторить запрос.

## GitHub Pages

1. Создайте GitHub-репозиторий и отправьте файлы в ветку `main`.
2. Settings → Pages → Source: GitHub Actions.
3. Settings → Secrets and variables → Actions → Variables: добавьте `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.
4. Запустите Deploy to GitHub Pages. Без переменных будет опубликовано только демо.

## Проверки

```sh
npm test
npm run build
```

После подключения базы проверьте двумя разными браузерами: запись, приоритет, вход преподавателя, перенос в конец, допзадание и возврат, отказ студенту при попытке вызвать административный RPC. Автоматические тесты проверяют порядок очереди и выполняют SQL в PostgreSQL через PGlite: права студентов, счётчики, историю, завершение сессий, устаревшие запросы и перенос старой очереди. Авторизация Supabase и доступ между устройствами требуют проверки на вашем проекте.

## Сессии и история

Одновременно открыта одна сессия с датой и группой. Преподаватель завершает её перед созданием следующей. Завершение сохраняет сдавших, ушедших и незавершённые записи; новая сессия начинается с пустой очереди. История доступна только преподавателю, студенты видят текущую сессию и очередь. Счётчик относится к записи на конкретную лабораторную в сессии; новая запись создаёт отдельную строку истории. Данные старой очереди при обновлении сохраняются в сессии «Перенесённая очередь», ранее совершённые повторы восстановить нельзя.

## Авторизация и QR

В открытой сессии преподаватель видит QR и ссылку. QR содержит URL сайта с ?session=UUID, без паролей и полномочий администратора. Студент открывает ссылку, регистрируется или входит и выбирает лабораторную. Старая ссылка блокирует запись в новую сессию. На сайте без параметра session также можно войти и записаться в открытую сессию; QR служит удобной ссылкой, а не доказательством присутствия.

В Supabase Authentication → URL Configuration задайте Site URL и Redirect URLs для опубликованного адреса и локальной разработки. При включённом подтверждении email регистрация покажет сообщение о письме; до подтверждения вход запрещён. Настройте SMTP для отправки писем студентам либо заранее создавайте подтверждённые аккаунты. Анонимный вход оставьте выключенным. При первой записи имя по умолчанию берётся из display_name аккаунта; его можно отредактировать в форме записи. Существующие строки истории сохраняют имя на момент сдачи.

QR на localhost не доступен с телефонов: открывайте опубликованный URL или сетевой адрес компьютера при общей Wi-Fi сети. Функции QR создаются локально, без передачи ссылки внешнему генератору.

Исторические завершённые записи до миграции 003 не имеют user_id: для них сохраняется история, но восстановление счётчика при повторной записи возможно только для записей, чья связь с аккаунтом известна.

## Обновление редактирования имени

Если миграция 003 уже выполнена, запустите только `supabase/migrations/004_editable_name.sql`. Для новой базы актуальный `schema.sql` включает это обновление. Имя сохраняется при нажатии «Встать в очередь». Само редактирование поля ничего не записывает.

Обновление очереди приостанавливается в скрытых вкладках и возобновляется сразу при возвращении. Параллельные запросы опроса не запускаются. После собственного действия изменения загружаются сразу. Скрипт PowerShell использует ASCII, чтобы работать и в Windows PowerShell 5.1 без проблем кодировки.

## Студенты не по графику

Для существующей базы выполните `supabase/migrations/008_off_schedule.sql` (после обновлений авторизации и сессий). Актуальная схема новой базы уже включает это изменение. При записи студент отмечает «Сдаю не по графику». Он ждёт в отдельном списке, пока в активной основной очереди есть студенты, включая повторные попытки. Сдавшие, ушедшие и выполняющие допзадание не блокируют допуск. После освобождения основной очереди ожидающие допускаются по порядку регистрации. Текущий сдающий не прерывается. Если основной студент возвращается с допзадания или записывается заново, ещё не начавшие сдачу студенты не по графику снова ожидают; готовые с допзадания сохраняют прежний приоритет. Отметка сохраняется в истории. Кнопка «Следующий» продолжает увеличивать счётчик и перемещать в конец. Признак другой группы указывается студентом самостоятельно.

## Единый экран входа

До авторизации сайт показывает только форму входа. Студент вводит выданный логин, преподаватель — свой email. После успешного входа и получения прав из queue_snapshot преподаватель автоматически видит админку, студент — открытую сессию и очередь. Параметр ?session из QR сохраняется при входе. После выхода экран сессии скрывается; повторное открытие с сохранённым входом восстанавливает интерфейс по роли. Локальный #admin больше не выбирает роль.

## Незавершённые допзадания

Обновление базы: `supabase/migrations/009_pending_extras.sql` после 008. При закрытии сессии результат extra остаётся «Доп. задание». Незавершённое задание привязано к аккаунту и лабораторной: при следующей записи на ту же работу студент сразу попадает в список допзаданий, сохраняет счётчик и возвращается кнопкой «Готово». Другая лабораторная не затрагивается. Для указанной преподавателем записи Доктурбекова за 21.10.2026 подготовлен отдельный `supabase/restore_dokturbekov_extra.sql`: он проверяет однозначность записи и сохраняет её первоначальное время. Ранее перезаписанные в unfinished результаты других студентов автоматически восстановить нельзя.

## Время создания сессии

Для существующей базы выполните `supabase/migrations/010_session_creation_time.sql` после 008. Новые сессии сохраняют серверное время создания (timestamptz), история отображает часы, минуты и секунды в часовом поясе браузера преподавателя. Для старых сессий created_at остаётся NULL: интерфейс показывает «время не сохранено» и короткий идентификатор, чтобы одинаковые группы различались. Реальное старое время создания восстановить из одной даты сдачи нельзя.

## Superadmin и преподаватели

1. В SQL Editor выполните по порядку supabase/migrations/012_superadmin_delete_session.sql и supabase/migrations/013_manage_teachers.sql.
2. В Authentication → Users → Add user создайте superadmin@mail.ru, задайте свой пароль и включите Auto Confirm. Если аккаунт уже есть, пересоздавать его не нужно.
3. Выполните supabase/grant_superadmin.sql. Он выдаёт роль только указанному email, существующих преподавателей не повышает.
4. Опубликуйте Edge Function create-teacher из supabase/functions/create-teacher/index.ts. Из терминала проекта с установленным Supabase CLI:

```powershell
npx supabase login
npx supabase functions deploy create-teacher --project-ref udqcajzvfklmiiviorbv --no-verify-jwt
```

Gateway JWT check отключается для совместимости с ES256. Внутри функции каждый запрос обязательно проверяется через auth.getUser и queue_is_superadmin. Встроенные серверные переменные SUPABASE_URL, SUPABASE_ANON_KEY и SUPABASE_SERVICE_ROLE_KEY используются только в Edge Function; в браузер не передаются. Настройка CLI также записана в supabase/config.toml.

Войдите в сайт как superadmin@mail.ru: в истории появится «Удалить сессию» и ниже форма «Создать преподавателя». Удаление доступно только для завершённых сессий и удаляет историю именно выбранной сессии. Незавершённые допзадания сохраняются независимо от истории. Форма создания преподавателя запрашивает имя, email и пароль, создаёт подтверждённый аккаунт без письма и выдаёт обычные преподавательские права. Существующие email не перезаписываются. Пароль superadmin не хранится в исходниках.

Сборка интерфейса и тесты базы проверяются локально. Саму Edge Function нужно дополнительно проверить после публикации в вашем проекте Supabase.

## Отдельные сессии преподавателей

Для существующей базы выполните только supabase/migrations/014_teacher_sessions.sql после 013. Обновлённый schema.sql уже включает это изменение для новой базы. После 014 нельзя повторно применять старые миграции функций 002–013: они рассчитаны на прежнюю общую очередь.

Каждый преподаватель открывает одну свою активную сессию. Очередь, текущий студент, актуальная лабораторная, счётчики и история изолированы по сессии. Незавершённые допзадания теперь относятся к конкретному преподавателю, студенту и лабораторной. Преподаватель не может читать историю и управлять сессией коллеги; superadmin может выбирать любую активную сессию и по-прежнему удаляет только завершённые.

Студенты выбирают преподавателя из списка активных сессий или открывают QR. Новый клиент не открывает случайную очередь автоматически. Один аккаунт может иметь отдельные записи в разных сессиях. При переключении сессии URL обновляется, а действия передают выбранный session_id; сервер проверяет владельца независимо от интерфейса. Старый RPC queue_snapshot() сохранён для совместимости; новый клиент использует queue_snapshot_for_session(uuid).

Миграция переносит текущие записи и актуальную лабораторную из старой общей очереди. Существующий created_by сохраняется. Если владелец старой сессии не был записан, назначение возможно автоматически только при единственном преподавателе. Остальная история без владельца сохраняется и видна superadmin; автоматически приписывать её случайному преподавателю нельзя. Аналогично незавершённые задания с неизвестным преподавателем сохраняются, но не назначаются другому преподавателю произвольно.

Публиковать create-teacher заново для этого обновления не требуется: функция создания преподавателей не изменилась.

## Постоянная отметка допзадания

После 014 выполните `supabase/migrations/015_extra_markers.sql`. Флаг «Был на допзадании» сохраняется после «Готово», «Следующий», повторной записи в ту же сессию и в истории. Перенесённое задание помечается «Доп. с прошлой сессии»: после готовности студент идёт в конец очереди без приоритета. Задание, выданное текущей сессией, сохраняет прежний приоритет возврата. Начальный перенос флага для старых записей возможен только там, где сохранился статус extra; ранее затёртые сведения о допзадании автоматически восстановить нельзя.

## Медали лабораторной

После 015 выполните `supabase/migrations/016_lab_medals.sql`. 🧠 начисляется только за каждое нажатие преподавателем «Доп. задание», сохраняется между сессиями у того же преподавателя по той же лабораторной; перенос и «Готово» новую медаль не добавляют. 🔄 показывает счётчик «Следующий». 🥇 сохраняется сервером при сдаче с первой попытки без допзаданий, повторов и предыдущих зафиксированных сдач/неудач этой работы. При завершении сессии оставшиеся в очереди получают результат failed (💀 «Не защитил»), extra продолжает переноситься. Ранее сохранённые unfinished не меняются. Исторический булев флаг допзадания позволяет восстановить минимум одну 🧠, но не неизвестное точное число выдач. Легенда значков доступна под очередью.

## Отмена готовности к допзаданию

После 016 выполните `supabase/migrations/017_return_to_extra.sql`. После «Готово» студент видит «Вернуться к допзаданию». Действие доступно только для собственной записи и возвращает в статус extra без новых медалей и повторов; восстанавливается перенос незавершённого задания. Если студент уже текущий, очередь автоматически выбирает следующего. После нового преподавательского «Следующий» отмена прежней готовности уже недоступна. Перенесённое допзадание сохраняет возврат в FIFO, текущее — обычный приоритет допзадания.

## Вызов студентов не по графику по одному

После 017 выполните `supabase/migrations/018_admit_off_schedule.sql`. В списке «Не по графику» у преподавателя есть кнопка «Вызвать в очередь». Она доступна только при отсутствии current и waiting в этой сессии. Студенты в extra не блокируют вызов. Выбранный студент становится current, остальные deferred не переводятся автоматически. Новые студенты не по графику сначала попадают в deferred. Возврат готового допзадания сохраняет прежние правила. Административный вызов не увеличивает счётчики медалей или повторов.
